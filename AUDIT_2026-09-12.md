**Объём проверки:** работоспособность (реальный прогон), безопасность и архитектура, соответствие законодательству РФ + сравнение с ЕС/GDPR

## 0. Вердикт в двух абзацах

**Технически** приложение работает частично. Из 19 проверенных страниц три падают с ошибкой 500 (`/leaders/`, `/quick-help/`, `/my-donations/`), завершение сбора средств всегда отдаёт 500, а в REST API для мобильного приложения нерабочи обе денежные операции — перевод и пожертвование возвращают 500 из-за смешивания `Decimal` и `float` (чтение, регистрация и авторизация в API при этом работают). Криптовалютный модуль не запускается в принципе — оба провайдера не реализуют абстрактные методы базового класса.

**По безопасности** ситуация критическая и делает запуск в прод недопустимым. Два вебхука (`/payment/webhook/` и `/payment/crypto-callback/`) не проверяют подпись: **я воспроизвёл зачисление 50 000 ₽ и затем 1 000 000 ₽ на баланс обычным POST-запросом без авторизации**. Номера банковских карт, ФИО и паспортные данные хранятся в БД открытым текстом (модуль шифрования написан, но нигде не подключён). Файл `.env` закоммичен в git. **По праву** модель «внутренний рублёвый баланс + переводы между пользователями + вывод на карту» — это выпуск и перевод электронных денежных средств, который по ст. 12 161-ФЗ вправе осуществлять только кредитная организация. Работа без лицензии — состав ст. 172 УК РФ. Приём USDT прямо запрещён. Это не «доработать к релизу», а необходимость менять бизнес-модель.

## 2. Критические уязвимости

### 2.1 Подделка вебхука ЮKassa → зачисление любой суммы `views.py:999–1066`

```python
@csrf_exempt
def payment_webhook(request):
    body = json.loads(request.body)
    if body.get('event') == 'payment.succeeded':
        payment_id = body.get('object', {}).get('id')
        payment_tx = PaymentTransaction.objects.get(payment_id=payment_id)
        ...
        balance.amount += payment_tx.amount   # деньги зачислены
```

Нет ни проверки подписи, ни проверки IP из списка ЮKassa, ни обращения к `Payment.find_one()` для подтверждения статуса. `PAYMENT_WEBHOOK_SECRET` объявлен в настройках и **нигде не используется**.

**Воспроизведено:** POST без авторизации → баланс 98 500 ₽ → 148 500 ₽. Ответ `200 {"status":"ok"}`.
Угадывать `payment_id` атакующему, скорее всего, не придётся: это идентификатор платежа ЮKassa, который платформа получает при создании платежа и который фигурирует в процессе оплаты. Достаточно начать пополнение на 1 ₽, узнать id, отменить оплату и отправить вебхук.

### 2.2 Крипто-вебхук: сумма зачисления берётся из тела запроса `views.py:1082–1160`

```python
amount_rub = Decimal(payload.get('amount_rub', '0'))   # ← из запроса атакующего
rub_balance.amount += amount_rub
```

Здесь сумма даже не сверяется с `PaymentTransaction.amount`. Комментарий «Проверка подписи (если настроена)» стоит над кодом, который ничего не проверяет.

**Воспроизведено:** платёж на 1 ₽, в payload указано `amount_rub: 1000000` → баланс вырос с 148 500 до **1 148 500 ₽**.

Дополнительно: `Balance.objects.select_for_update()` (строка 1137) вызывается **вне** `transaction.atomic()` — на PostgreSQL это `TransactionManagementError`, на SQLite молча проходит без блокировки.

### 2.3 Номера карт и паспорта в открытом виде

Паспортные данные лежат в БД как есть — реальная запись из вашего `db.sqlite3`:

```
UserVerification: ('0321', '868151', 'Канцев Андрей Викторович')
```

Реквизиты карты записываются в `JSONField` без какой-либо обработки (`views.py:803–808`):

```python
payment_details = {
    'card_number': form.cleaned_data.get('card_number'),
    'card_holder':  form.cleaned_data.get('card_holder'),
    'expiry_date':  form.cleaned_data.get('expiry_date'),
}
```

Заявок на вывод в вашей БД пока нет, поэтому реальных PAN там тоже нет — но в моём тестовом прогоне заявка сохранилась как `{'card_number': '4111111111111111', 'card_holder': 'IVAN IVANOV', 'expiry_date': '12/29'}`, то есть первый же боевой вывод положит в базу полный номер карты открытым текстом.

При этом `main/utils/encryption.py` (Fernet) написан — и не импортируется **ни в одном** файле проекта. README раздел «Шифрование реквизитов карт» описывает `'card_number': 'encrypted:gAAAAAB...'` — в коде этого нет.

Хранение полного PAN + срока действия — прямое нарушение PCI DSS; для вывода средств хранить PAN вообще не требуется, достаточно токена платёжного провайдера. Плюс это утечка ПДн в смысле ст. 13.11 ч. 12–15 КоАП.

### 2.4 `.env` в git; дефолтные секреты

`git ls-files` показывает `.env` среди отслеживаемых файлов, а `.gitignore` содержит только `logs/` и `*.log`. Сейчас в `.env` заглушки (`your-...`), но как только туда лягут боевые ключи ЮKassa — они уйдут в историю репозитория.

`SECRET_KEY`, `ENCRYPTION_KEY` (`'your-encryption-key-here'` — невалидный ключ Fernet, `get_cipher()` упадёт при первом же вызове) и `PAYMENT_WEBHOOK_SECRET` имеют небезопасные значения по умолчанию, то есть при отсутствии переменных окружения прод поднимется с известным всем ключом подписи сессий.

### 2.5 2FA не применяется при входе

**Воспроизведено:** включил `TwoFactorAuth.is_enabled = True`, вошёл логином и паролем — вход выполнен, код не запрошен. `login_page` (`views.py:114`) вообще не обращается к модели `TwoFactorAuth`. Функция существует только в виде страницы настройки.

### 2.6 Нет защиты от перебора паролей

**Воспроизведено:** 12 неверных паролей подряд — все ответы 200, блокировки нет. `AntiFraudService` есть, но при неудачном входе не вызывается; `SecurityLog` с типом `failed_login` не пишется. Вместо этого в stdout идёт `print(f"Failed login attempt for {username}")` — имена пользователей утекают в логи сервера.

Throttling DRF (`anon: 100/day`) на веб-формы не распространяется.

### 2.7 Refresh-токены невозможно отозвать

`SIMPLE_JWT` включает `BLACKLIST_AFTER_ROTATION: True`, но приложения `rest_framework_simplejwt.token_blacklist` **нет в `INSTALLED_APPS`** (проверено). В `LogoutView` вызов `token.blacklist()` падает и глушится `except Exception: pass`, возвращая пользователю «Успешный выход». Фактически украденный refresh-токен живёт 7 дней, и разлогинить его нельзя.

### 2.8 Stored XSS в админ-панели `admin.py:296`

```python
return mark_safe(f'<a href="...">{obj.fundraise.title}</a>')
```

Название сбора вводит пользователь и оно вставляется в HTML без экранирования. **Воспроизведено:** сбор с названием `<img src=x onerror=alert(1)>` попадает в `/admin/main/donation/` в сыром виде.

Всего в `admin.py` 37 вызовов `mark_safe`; эксплуатируемых из них три — `fundraise_link` (296) и в `payment_details_display` строки 403 (`👤 Владелец: {value}` — имя держателя карты) и 411 (ветка `else`, куда попадает `expiry_date`). Остальные подставляют числа и значения из `choices`, а `username` ограничен валидатором Django. Цена — исполнение JS в сессии администратора, то есть полный захват админки.

## 4. Финансовая логика: ошибки учёта

### 4.1 Лимиты верификации не работают вообще

Объявлены три уровня и лимиты (`UNVERIFIED_LIMITS['single_withdrawal'] = 500 ₽`), написаны два независимых валидатора — и **ни один не вызывается** из `create_withdrawal_request`. Вью делает свои, более слабые проверки: `MIN/MAX_WITHDRAWAL_AMOUNT` и «не более 3 заявок в день».

**Воспроизведено:** неверифицированный пользователь создал заявку на вывод 100 000 ₽ при заявленном лимите 500 ₽.

### 4.2 KYC — фикция

**Воспроизведено:** ввёл произвольные «1234 / 567890» и любое ФИО из русских букв → уровень мгновенно стал `basic`. Проверяются только регулярки на 4 и 6 цифр. Загруженный скан документа никак не связан с присвоением уровня; администратор одним действием ставит `full` без открытия документов.

### 4.3 Пополнение баланса в тестовом режиме не ограничено

`USE_REAL_PAYMENTS=False` (текущая настройка) означает: POST на `/topup/` просто увеличивает баланс. Лимит 100 000 ₽ — **на один запрос**, не суммарный. **Воспроизведено:** два запроса → 200 000 ₽ из ничего. Отрицательная сумма отсекается, нечисловая роняет сервер (п. 11 выше).

Если такой код доедет до прода с ошибочной переменной окружения — это бесконечная эмиссия денег.

### 4.4 Гонка при пожертвовании → отрицательный баланс

`views.py:546–560`: баланс проверяется **до** `atomic()`, а внутри блока после `select_for_update()` повторной проверки нет:

```python
user_balance = Balance.objects.select_for_update().get(user=request.user)
user_balance.amount -= amount      # проверки нет
```

В переводе (`views.py:215`) такая проверка есть — в пожертвовании её забыли. Два параллельных запроса на PostgreSQL уведут баланс в минус. То же в обоих API-методах.

### 4.5 Отмена сбора не возвращает деньги донорам

`cancel_fundraise` (`views.py:882`) меняет статус и оставляет комментарий: «средства уже на счету автора». Пользователь может собрать деньги на «лечение», отменить сбор и вывести средства. Механизма возврата нет ни в коде, ни в оферте. Это готовая схема мошенничества (ст. 159 УК) с прямой ответственностью площадки.

### 4.6 Комиссия: код противоречит оферте

| Источник | Комиссия за пожертвование |
|---|---|
| Пользовательское соглашение (п. 3.2) | **3 %** |
| README («Финансовая модель») | **3 %** |
| Веб-интерфейс, `views.py:613` | **0 %** |
| REST API, `api/views.py:177` | **3 %**, но удержанные деньги **никуда не зачисляются** — просто исчезают из системы |

Модель `CommissionTransaction` осталась в БД, но не используется нигде. Формально противоречие «3 % в оферте / 0 % в коде» не проявляется у пользователя только потому, что ветка с 3 % недостижима — метод падает строкой раньше (см. п. 6 раздела 3). Как только API починят, одна и та же операция станет давать разный результат с сайта и из мобильного приложения. В любом случае фактическая цена услуги не соответствует публичной оферте — ст. 10 ЗоЗПП, ч. 1 ст. 14.8 КоАП.

### 4.7 Прочее по учёту

* Пополнение записывается как `Transaction(sender=user, receiver=user)` — в истории это выглядит как перевод самому себе, а в рейтинге такие суммы попадают одновременно в «отправлено» и «получено», завышая обороты
* `Balance.amount` — `max_digits=10` → максимум 99 999 999.99 ₽; на PostgreSQL переполнение даст `DataError`, на SQLite значение запишется и упадёт `decimal.InvalidOperation` уже при чтении
* `Balance.amount` не имеет ограничения `>= 0` на уровне БД
* `Fundraise.current_amount`/`donors_count` обновляются без `select_for_update()` — счётчики разъезжаются при параллельных донатах
* `WithdrawalRequest.reject()`/`cancel()` возвращают деньги без `atomic()` и без блокировки строки
* В админке `list_editable = ['status']` позволяет перевести заявку в `rejected` **в обход** метода `reject()` — деньги не вернутся
* Реальной выплаты не происходит нигде: `MassWithdrawalService` не вызывается ни из админки, ни откуда-либо ещё (проверено `grep`), а действия «Подтвердить» и «Завершить» просто меняют статус. `WithdrawalRequest.approve()` содержит комментарий «Здесь должна быть интеграция с платежной системой». То есть заявка помечается выполненной без перевода денег
* `admin.py`: `mark_as_completed` меняет статус транзакций пачкой, не трогая балансы — рассинхронизация истории и остатков
* `check_username` использует `username__icontains` — на запрос `z` отвечает `{"exists": true}`; логика проверки занятости имени неверна

## 5. Архитектура и качество кода

**Что сделано хорошо.** Модель согласий с версионированием, IP, User-Agent, отзывом и отдельным журналом `ConsentLog` — редкая для учебных проектов проработка. Правильно используется `select_for_update()` в переводах. Админка подробная, с фильтрами и действиями. Разделение платёжных провайдеров через абстрактный базовый класс — верная идея (испорченная нереализованными методами).

**Проблемы:**

* `views.py` — 1 378 строк, вся логика переводов, платежей, KYC и 2FA в одном файле; бизнес-логика внутри вью, а не в сервисном слое
* Нет `requirements.txt` / `pyproject.toml` — воспроизвести окружение невозможно, я подбирал пакеты вручную
* `main/tests.py` — 3 строки, тестов нет ни одного. Все 14 дефектов из раздела 3 нашлись бы первым же smoke-тестом
* Дублирование: `MockPaymentProvider` определён дважды (`base.py:30` и `yookassa.py:222`), лимиты верификации скопированы в трёх местах (`settings.py:264`, `verification.py:41`, `withdrawals.py:305`) — сейчас значения совпадают, но любое изменение придётся вносить трижды
* Мёртвый код: `main/payments/sbp.py` и `stripe.py` пусты, `SBPProvider = YooKassaProvider`, `StripeProvider = MockPaymentProvider`, `utils/encryption.py` не используется, `CommissionTransaction` не используется
* `print()` вместо логирования в `register_page`, `login_page`, `yookassa.py`
* `except Exception` с показом `str(e)` пользователю (`views.py:235, 599`) — утечка внутренних деталей
* `random.choice(list(active_users))` в `quick_help` (`views.py:438`) материализует всех пользователей в память
* SQLite как рабочая БД: `select_for_update()` на нём не даёт построчных блокировок, то есть вся защита от гонок существует только на бумаге до перехода на PostgreSQL
* Нет `ATOMIC_REQUESTS`, нет индексов на часто фильтруемых полях, нет `CONN_MAX_AGE`
* `DEBUG` по умолчанию `True`, `ALLOWED_HOSTS = ['*']` при `DEBUG=True`
* `media/` (сканы паспортов) не отдаётся Django и не защищён — при настройке nginx «как обычно» документы окажутся публично доступны по прямой ссылке
* `CACHES` — `LocMemCache`: любые счётчики и антифрод-лимиты не переживут перезапуск и не будут общими между воркерами

## 6. Правовой анализ — Российская Федерация

> Ниже — обзор правовых рисков, а не юридическое заключение. Я не юрист; перед любыми действиями нужна консультация практикующего специалиста по финансовому праву.

### 6.1 Главное: модель требует банковской лицензии

Внутренний рублёвый баланс, который пополняется деньгами, переводится между пользователями и выводится на карту, — это **электронные денежные средства** (п. 18 ст. 3 161-ФЗ). Ст. 12 161-ФЗ: становиться обязанным по ЭДС и осуществлять их перевод вправе **только кредитная организация**. Ст. 11: оператором по переводу денежных средств — тоже только КО.

Название «виртуальная внутренняя валюта» (как в README) квалификацию не меняет: обратимость 1:1 в рубли и возможность вывода — определяющий признак.

**Ответственность:** ст. 172 УК РФ (незаконная банковская деятельность) — до 4 лет лишения свободы по ч. 1; по ч. 2 (организованная группа либо доход свыше 13,5 млн ₽) — до 7 лет и штраф до 1 млн ₽. Порог крупного размера — свыше 3,5 млн ₽ (прим. к ст. 170.2 УК в ред. 79-ФЗ от 06.04.2024). Параллельно — ч. 2 ст. 14.1 КоАП (деятельность без лицензии). Ст. 15.26 КоАП неприменима: она адресована самим кредитным организациям.

Отдельный риск: схема «пополнил → перевёл другому → тот вывел» архитектурно совпадает со схемами обналичивания и финансовых пирамид → внимание по ст. 172.2 УК и ст. 14.62 КоАП.

**Лимиты ЭСП по ст. 10 161-ФЗ**, которые в любом случае нарушены:

| Вид ЭСП | Остаток | Оборот/мес | В приложении |
|---|---|---|---|
| Без идентификации | 15 000 ₽ | 40 000 ₽ | **без ограничений**, пополнение до 100 000 ₽ за раз |
| Упрощённая идентификация | 100 000 ₽ | 200 000 ₽ | — |
| Полная идентификация | 600 000 ₽ | — | — |

*(лимит 100 000 ₽ при упрощённой идентификации — ФЗ от 29.05.2024 № 122-ФЗ, действует с 30.05.2025)*

### 6.2 115-ФЗ (ПОД/ФТ) — не реализовано ничего

Формально «веб-платформы взаимопомощи» нет в закрытом перечне ст. 5 115-ФЗ — но это не защита, а следствие того, что деятельность ведётся вне правового поля: при легализации в любом пригодном статусе обязанности возникают автоматически.

Отсутствует: постановка на учёт в Росфинмониторинге, ПВК по ПОД/ФТ, специальное должностное лицо, идентификация (см. 4.2 — она имитируется), сверка с перечнем террористов и экстремистов не реже раза в квартал, фиксирование и направление сведений об операциях от 1 000 000 ₽ (ст. 6), хранение документов 5 лет, механизм блокировки.

`AntiFraudService.check_withdrawal` — две проверки (сумма > 50 000 ₽ и > 5 выводов в день), результат которых **нигде не используется**: метод не вызывается из вью создания заявки.

Санкции — ст. 15.27 КоАП: от 50–100 тыс. ₽ (ч. 1) до 700 тыс. – 1 млн ₽ с приостановлением деятельности до 90 суток (ч. 3, 4).

### 6.3 152-ФЗ — нарушения по всем ключевым пунктам

**Согласие (ст. 9, ред. с 01.09.2025)** должно быть конкретным, предметным, информированным и **оформленным отдельно от иных документов**. У вас три чекбокса при регистрации, объединяющие политику, оферту и cookies; ни в одном нет обязательных реквизитов ч. 4 ст. 9 (наименование и адрес оператора, цель, перечень ПДн и действий, срок и порядок отзыва). **Регистрация через API (`/api/auth/register/`) не собирает согласий вообще** — воспроизведено: `UserConsent.objects.count() == 0` после регистрации.

**Согласие на распространение (ст. 10.1)** требуется отдельно и не может быть частью общего. `/api/leaders/` публикует username и суммы **без авторизации**, страницы сборов публичны — такого согласия нет.

**Политика конфиденциальности не соответствует действительности.** Заявлено: username, email, пароль, история транзакций, IP, браузер. Фактически собирается: **ФИО, дата рождения, серия и номер паспорта, адрес, скан документа, номер банковской карты и срок её действия, СНИЛС, ИНН**. Утверждение «Мы не передаём ваши персональные данные третьим лицам» ложно — код передаёт данные в ЮKassa, CryptoBot (Telegram) и CoinGecko. Не указан оператор (наименование, ИНН, адрес) — при этом ст. 18.1 152-ФЗ требует публикации политики, а ст. 14 — предоставления этих сведений субъекту.

**Уведомление Роскомнадзора** об обработке ПДн (ст. 22) — обязательно с 01.09.2022 без исключений, подаётся до начала обработки. Судя по всему, не подавалось.

**Трансграничная передача (ст. 12)** — отдельное уведомление РКН до начала передачи. CryptoBot (Telegram) и CoinGecko — иностранные сервисы; Stripe в настройках тоже.

**Локализация (ч. 5 ст. 18)** — БД должна находиться в РФ. В dev это SQLite локально; при выборе хостинга это критично.

**Уведомление об утечке** — 24 часа на факт, 72 часа на результаты расследования (ч. 3.1 ст. 21). Процедуры нет.

**Право на удаление** — `UserConsent.revoke()` только ставит флаг; данные, включая паспорт и карту, остаются в БД. Команда `clear_test_users` затрагивает только тестовых пользователей.

**Штрафы по ст. 13.11 КоАП** (реформа 420-ФЗ, действует с 30.05.2025) — для юрлица:

| Состав | Штраф |
|---|---|
| Обработка без согласия (ч. 2) | 300–700 тыс. ₽ |
| Неуведомление РКН об обработке (ч. 10) | 100–300 тыс. ₽ |
| Несообщение об утечке в 24 ч (ч. 11) | 1–3 млн ₽ |
| Утечка 1–10 тыс. субъектов (ч. 12) | 3–5 млн ₽ |
| Нарушение локализации (ч. 8 / повторно ч. 9) | 1–6 млн / 6–18 млн ₽ |
| Повторная утечка (ч. 15, оборотный) | 1–3 % выручки, не менее 20–25 млн, до 500 млн ₽ |

Скидка 50 % за быструю уплату к ст. 13.11 не применяется.

**Ст. 272.1 УК РФ** (введена 421-ФЗ, действует с 11.12.2024) — незаконные сбор, хранение, использование или передача ПДн: ч. 1 — до 4 лет, ч. 3 (корысть, крупный ущерб, группа) — до 6 лет, ч. 4 (трансграничная передача) — до 8 лет. С учётом того, как в приложении хранятся паспорта и карты, это не теоретическая статья.

### 6.4 Криптовалюта — прямой запрет

С 01.09.2026 действует ФЗ от 04.08.2026 № 282-ФЗ «О цифровых валютах и цифровых правах». Цифровая валюта признана имуществом, ЦБ РФ ведёт реестры участников. **Запрет на использование цифровой валюты как средства платежа и встречного предоставления за товары, работы и услуги в РФ сохранён** (ранее — ч. 5 ст. 14 259-ФЗ от 31.07.2020). Исключения — внешнеторговые контракты через ЭПР Банка России, вознаграждение за майнинг, сетевые комиссии.

Пополнение внутреннего баланса за USDT — это встречное предоставление, то есть прямо запрещённая операция. Систематический приём крипты в обмен на рублёвый баланс — ещё и деятельность обменника, требующая включения в реестр ЦБ (с 01.07.2027 банки обязаны блокировать переводы неавторизованным операторам).

Отдельного состава именно за нарушение этого запрета нет; риски реализуются через ст. 172 УК, ч. 2 ст. 14.1 КоАП, налоговую переквалификацию со штрафом до 40 % (ст. 122 НК) и внимание Росфинмониторинга.

**Практический вывод: USDT из схемы нужно убрать полностью.** Тем более что модуль всё равно не работает (п. 7 раздела 3).

### 6.5 Сборы средств

Физлицо вправе принимать пожертвования — ст. 582 ГК. Ограничения 135-ФЗ адресованы благотворительным организациям; ст. 16.1 (ящики для сбора пожертвований) касается только физических ящиков для наличных и на онлайн-сборы не распространяется. 259-ФЗ от 02.08.2019 об инвестиционных платформах неприменим — он покрывает займы, ценные бумаги, УЦП и ЦФА, но не безвозмездные пожертвования. Специального регулирования donation-краудфандинга в РФ на сентябрь 2026 нет.

**Но конкретно в этой реализации риски высокие:**

* Модерации сборов нет: любой создаёт сбор «Медицина» на 10 млн ₽ мгновенно, без документов и проверки цели
* Отчётности о расходовании нет
* Возврата при отмене сбора нет (см. 4.5) — при нецелевом использовании это ст. 159 УК для организатора и риск соучастия/гражданских исков для площадки
* `is_featured` («Рекомендуемый») выставляется администратором без каких-либо критериев — фактическое поручительство площадки за сбор

### 6.6 Налоги

Дарение денег между физлицами полностью освобождено от НДФЛ независимо от родства (п. 18.1 ст. 217 НК) — это работает в пользу вашей модели, **пока платёж действительно безвозмезден**. Как только за донат обещано встречное предоставление, это доход по ст. 208/209 НК и облагается по прогрессивной шкале 13–22 %.

Платформа, лишь технически посредничающая при дарении между физлицами, налоговым агентом не является. **Но** удержание комиссии и участие в расчётах (а у вас деньги реально проходят через баланс площадки) существенно повышают риск признания площадки и агентом, и налогоплательщиком по всему обороту.

Отдельно: с 01.10.2026 действует ФЗ от 31.07.2025 № 289-ФЗ «Об отдельных вопросах регулирования платформенной экономики». Он распространяется на операторов посреднических цифровых платформ и требует раскрытия условий ценообразования и правил работы алгоритмов ранжирования, уведомления партнёров за 45 дней при повышении вознаграждения платформы, досудебного механизма рассмотрения жалоб (ответ 15 дней, устранение 48 часов). Ваша модель с высокой вероятностью попадает под него.

### 6.7 Требования к сайту

* **Ч. 2 ст. 10 149-ФЗ** — обязательное раскрытие сведений о владельце сайта (наименование, адрес, email). На сайте их нет
* **Ст. 8 и 10 ЗоЗПП** — достоверная информация об услуге и **цене в рублях**. Расхождение «3 % в оферте / 0 % на сайте / 3 % в API» это нарушает. Санкция — ч. 1 ст. 14.8 КоАП (до 10 тыс. ₽ на юрлицо), ч. 2 — за условия, ущемляющие права потребителя (до 20 тыс. ₽)
* **Оферта (ст. 437 ГК)** — текущий текст содержит взаимоисключающие положения: «Сервис не является финансовым посредником» (фактически является), «Запрещается обналичивание денежных средств» (вывод на карту — ровно оно), запрет отмывания без единого механизма его выявления
* **Возраст.** Проверки нет. Сделки несовершеннолетних за пределами мелких бытовых требуют согласия законных представителей (ст. 26, 28 ГК). Нужен прямой запрет регистрации младше 18 в оферте и хотя бы декларативная проверка
* **Реклама финансовых услуг** (ст. 28 38-ФЗ) — требует указания лица, оказывающего услуги; обещание доходности запрещено

| Прозрачность, ст. 13 | Политика не раскрывает категории данных, сроки хранения, получателей, права субъекта |

| DPO, ст. 37 | Не назначен, хотя масштабная обработка финансовых данных — вероятное основание |

**PSD2 / EMD2:** выпуск электронных денег в ЕС требует лицензии EMI, перевод средств — PI. Ситуация зеркальна российской: без лицензии модель нелегальна. У вас 2FA реализована как страница настройки и при входе не проверяется (п. 2.5).

|---|---|
| Регистрация через веб-форму | OK, 3 согласия записаны с IP и User-Agent |
| Регистрация через API | OK, **0 согласий**, пароль `12345678` принят |
| Пополнение 100 000 ₽ × 2 | OK, баланс 200 000 ₽ — лимита на суммарное пополнение нет |
| Пополнение «abc» | **500 InvalidOperation** |
| Пополнение −500 ₽ | Корректно отклонено |
| Перевод между пользователями (веб) | OK |
| Перевод через API | **500 Decimal/float** |
| Создание сбора | OK |
| Пожертвование (веб) | OK |
| Пожертвование через API | **500 Decimal/float** |
| Завершение сбора | **500 NameError: floatformat** (статус при этом сохраняется) |
| Заявка на вывод 100 000 ₽ без верификации | **Принята** (заявленный лимит — 500 ₽) |
| Поддельный вебхук ЮKassa | **+50 000 ₽, ответ 200** |
| Поддельный крипто-вебхук | **+1 000 000 ₽, ответ 200** |
| 12 неверных паролей подряд | Все 200, блокировки нет |
| Вход при включённой 2FA | Выполнен **без кода** |
| Самостоятельная KYC | Уровень `basic` за произвольные «1234/567890» |
| XSS в админке через название сбора | Payload попадает в HTML **без экранирования** |
| `/api/users/` от рядового пользователя | Email и балансы **всех** пользователей (21 в вашей БД) |
| `/api/leaders/` без авторизации | Username, обороты и **балансы** |
| Страницы `/leaders/`, `/quick-help/`, `/my-donations/` | **500** |
| Остальные 16 страниц | 200 |
